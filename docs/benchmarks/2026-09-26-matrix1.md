## Reading — what holds and what does not yet

1. **Throughput: neton epoll ×4 leads** from 12 connections up (1.2–2.6× geario) and ties at 1 connection.
2. **\* The epoll p99 at 100–1000 connections is not credible yet.** 22 µs at 1000 connections, when geario
   shows 8.5 ms, is more likely unfairness hidden by the client than a real tail: the client records latency
   only for requests that *complete*, so connections that are starved contribute few samples. Drain-to-EAGAIN
   (§17) keeps serving a ready fd, which could favour some connections. Before any latency claim: per-connection
   completion counts (min / median / max) for both servers.
3. **io_uring collapses at 64 KB** (25 qps, p99 ≈ 42 ms at 1 connection). The constant ~42 ms looks like the
   delayed-ACK timer, i.e. a stall that only a timer ends. epoll is unaffected, so it is in the uring path
   (multishot recv with 16 KB provided buffers, or the SEND SQE path for large writes). To diagnose next.
4. **Memory: neton uses ~5× geario per connection** (≈130 KB vs ≈22 KB at 1000 connections; idle 10–13 MB vs
   3 MB). The echo server holds a 64 KB `Buffer` per connection for its lifetime; geario's buffers come from a
   pool and are held only while data is in flight. io_uring adds its provided-buffer pool (512 × 16 KB per
   reactor). A pooled / lazily held read buffer is an architecture item.

## Addendum: the epoll p99 at 1000 connections contradicts Little's law

With N closed-loop connections, one request in flight each and no think time, mean latency = N / X.
For epoll ×4 at 1000 connections, X ≈ 350,000/s ⇒ **mean latency ≈ 2.9 ms**, so a p99 of 22 µs is
impossible if every connection is served alike: most completed requests are fast only because a few
connections are served again and again while the rest wait. geario is consistent (1000 / 201,585/s ≈ 5.0 ms
mean, p99 8.5 ms).

Suspected mechanism (hypothesis until `echo-client-fair` measures per-connection counts): after `send()`
the kernel runs the woken client thread on the reactor's core; it sends its next request at once, so the
reactor's drain-to-EAGAIN `recv()` on that fd succeeds again and serves it again — a ping-pong pair
monopolises the core. Round 6b saw the same effect as "11 requests per wake". If confirmed, two earlier
conclusions change: part of epoll ×4's lead over geario (rounds 4–17 and this matrix) comes from unfair
service, and §17b's short-read rule was rejected for losing throughput that was itself unfair. **Until the
fairness data is in, the multi-core lead must not be quoted.**
